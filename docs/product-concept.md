## 1. 事業概要

### 1-1. 何を売るか

**新人・バイト向けの社内ナレッジ Q&A SaaS。**

顧客企業が持つ研修資料・業務マニュアル・社内規程を取り込み、新入社員やアルバイトが自然な言葉で質問すると、**会社の資料に基づいた回答**が返ってくるシステム。

### 1-2. 事業の中心命題

**LLM 進化で代替されない価値のうち、システムで実装できるものと、導入時に最小限必要な伴走だけを商品化する。**

AI モデルの性能は 1〜2 年で大きく進化する。モデル性能に依存した差別化（回答精度、プロンプト最適化など）は賞味期限が短い。我々が売るのは、**モデルが進化しても消えない価値**だけに限定する。

### 1-3. LLM 進化で消える価値 / 残る価値

| LLM 進化で消える（売らない） | LLM 進化で残る（売る） |
|---|---|
| 回答精度の高さ | 資料管理画面・正本フラグ・更新アラート |
| チャット UI の出来 | 自動カテゴリ分類・重複検出 |
| 検索アルゴリズムの工夫 | 未回答ログから資料不足を検知 |
| モデル選定・切替 | 質問傾向ダッシュボード |
| プロンプト職人芸 | 責任分界を定義する契約設計 |

### 1-4. なぜ標準 LLM（ChatGPT / Copilot）では代替されないか

1. **ChatGPT / Copilot は汎用アシスタント**であり、特定企業の業務の中には埋め込まれない
2. **資料がぐちゃぐちゃなままでは、どんな高性能 LLM でも正しく答えない**
3. **誰が何を更新するかが決まらないと、精度は必ず劣化する**
4. **AI に疎い会社は、自力で導入・運用設計ができない**
5. **責任分界を決めずに AI を業務に入れると、トラブル時に止まる**

## 2. ターゲット

### 2-1. 顧客像

**AI・システムに疎い会社。業種は問わない。**

- システム会社はターゲットにしない（中身を見て内製・模倣される）
- 疎い会社は仕組みを真似できないため、設計思想ごと売れる
- 運用サポート契約がそのまま継続収益になる
- 価格は「何ができるか」で決まり、技術原価でバレない

### 2-2. 最初の 6 ヶ月で解く痛み

**新人教育の立ち上がり遅延。**

他の痛み（属人化、拠点間の回答ブレ、規程確認ミス、社内問い合わせ工数）は初期 6 ヶ月では扱わない。1 つに固定して深く掘る。

**選定理由:**
- 効果が数値化しやすい（立ち上がり期間の日数）
- 人事・経営に説明しやすい（= 決裁が取れる）
- 業種横断で発生する（業種非依存方針と両立）
- 自社（GrowDays）で実データが取れる

### 2-3. 初期販売対象

**既存の開発代行顧客のみ。新規営業はしない。**

- 既に業務理解があり、提案精度が高い
- 信頼関係があり導入検証が通りやすい
- 新規営業は勝ち筋が固まってから（最短でも 6 ヶ月後）

## 3. プロダクトの UX

### 3-1. ユーザー向け画面（新入社員・バイトが使う画面）

ChatGPT / Claude 風の対話 UI を採用する。

```
┌──────────────────────────────────────────────┐
│  〇〇株式会社 社内ヘルプ                        │
├──────────────────────────────────────────────┤
│                                              │
│  💬 会話エリア                                │
│   - 質問と回答が積み上がる                     │
│   - 回答には出典リンクが付く                   │
│   - 「この回答は役に立ちましたか」ボタン         │
│                                              │
├──────────────────────────────────────────────┤
│ ← 有給申請の方法は │ 制服はどこ │ シフト変更 → │ ← よくある質問（自動横スクロール）
├──────────────────────────────────────────────┤
│ [質問を自由に入力してください...]      [送信] │
└──────────────────────────────────────────────┘
```

### 3-2. UX の設計原則

- **自然文で質問できる**（「有給って何日前に申請すればいいんですか？」で OK）
- **よくある質問が横に常時スクロール表示**
  - 「何を聞いていいか分からない」新人の入口になる
  - クリックで即座に質問が送信される
  - 質問候補は実際の質問ログから自動生成する
- **回答には必ず出典リンクを付ける**（「就業規則 第12条より」のように表示。クリックで該当資料を開ける）
- **質問履歴が残る**（自分のメモ代わりになる）
- **回答不能時の導線**
  - 「この質問には答えられませんでした」表示
  - Slack / Teams / メールでの人へのエスカレーションが可能

### 3-3. 管理者向け画面（顧客担当者が使う画面）

- **資料アップロード:**
  - PDF / Word / Markdown / Excel / テキスト
  - ドラッグ＆ドロップ対応
  - アップロード時に AI が自動でカテゴリ分類・タグ付け
- **正本管理:**
  - 「これが最新版」のフラグを立てる
  - 古いバージョンはアーカイブ（回答参照されない）
  - バージョン履歴が残る
- **重複検出:**
  - 似た内容の資料を自動検出
  - 「統合しますか？」の提案
- **更新アラート:**
  - 「この資料、半年更新されていません」通知
  - 有効期限を設定可能（例:「2026年度規程 → 2027/4/1 に要見直し」）
- **未回答ログ:**
  - 回答できなかった質問の一覧
  - 「この質問には◯◯の資料があれば答えられます」の自動提案
- **質問傾向ダッシュボード:**
  - カテゴリ別質問数
  - 時系列推移
  - 未回答率・自己解決率
  - エスカレーション率

## 4. 商品構成

### 4-1. 基本方針

- **我々はシステム屋**であり、コンサルは売らない
- ただし初期導入だけは最小限の伴走を行う
- 伴走は**定額・スコープ固定**で、コンサル化させない
- 月額運用は我々の工数が顧客数に比例しない構造にする
- **売るのは「回数・件数・時間で上限が切れるもの」のみ**

| 売る（導入支援 + システム） | 売らない（コンサル） |
|---|---|
| 初期資料のアップロード支援 | 業務プロセス全体のヒアリング |
| FAQ 候補 30 件の初期整備 | 業務 KPI 設計代行 |
| エスカレーション先ルールの初期設計 | 組織設計・役割分担提案 |
| 管理画面の使い方トレーニング | 人事制度への組み込み支援 |
| 「新人に何を答えさせたいか」の聞き取り | 経営課題の深掘り |
| 資料管理画面・正本フラグ・更新アラート | 導入前 ROI 試算コンサル |
| 未回答ログ・質問傾向ダッシュボード | 業種別カスタム業務分析 |

### 4-2. 商品1: 初期構築 + 導入支援パッケージ

#### システム構築

- システム導入・セットアップ
- 管理画面のテナント作成
- Slack / Teams 連携設定
- ブランディング調整（ロゴ・色・タイトル）

#### 導入支援パッケージ

| 内容 | 上限 | 時間目安 |
|------|------|---------|
| 業務キックオフ WS | 1 回 | 2 時間 |
| 初期資料のアップロード支援 | 50 件まで | 1 日 |
| FAQ 候補の初期整備 WS | 1 回 | 3 時間 |
| エスカレーション先ルール設計 WS | 1 回 | 2 時間 |
| 管理画面の操作トレーニング | 2 回 | 各 1 時間 |
| 稼働開始後のフォローアップ（初月のみ） | 2 回 | 各 1 時間 |

**合計: 2〜3 日分の工数。これを超える依頼は別途見積。**

- **価格帯:** 150〜350 万円
- **期間:** 1.5〜2 ヶ月

#### 顧客側の事前準備条件（導入支援の前提）

導入支援パッケージは、以下の前提条件を顧客が満たした状態で開始する。満たさない場合は別途スコーピングフェーズを設けるか、着手を延期する。

- **資料がフォルダ整理済み**（散在した状態での持ち込みは対象外）
- **最新版が顧客側で識別済み**（「どれが最新か分からない」状態は対象外）
- **テキスト抽出可能な形式**（スキャン画像のみの PDF は対象外。OCR 対応は別途見積）
- **FAQ 30 件の原案を顧客側で事前作成**（WS は原案のレビュー・確定の場に限定する）
- **決裁権限を持つ担当者の WS 同席**（その場で判断できる体制。持ち帰り前提は不可）
- **資料更新責任者 1 名を指名済み**（運用期の正本管理に必要）

### 4-3. 商品2: 継続運用サービス

- **月次レポート自動生成**（質問傾向・未回答率・自己解決率）
- **稼働監視・ホスティング**
- **機能アップデート提供**
- **テクニカルサポート**（画面の使い方レベル）
- **精度改善**（モデル更新・プロンプト調整）
- **更新アラートのシステム自動通知**
- **資料整備そのものは顧客が管理画面で行う**

**価格帯:** 月額 15〜40 万円

#### 運用期の追加支援メニュー（別料金）

月額運用は原則セルフサービスだが、顧客によっては追加支援が必要になる。これをコンサル化させず、都度課金で対応する。

| メニュー | 内容 | 価格目安 |
|---------|------|---------|
| スポット相談 | 未回答ログの対処・資料追加のアドバイス | 3 万円 / 時間 |
| スポット支援 | 資料追加アップロード代行・設定変更 | 15 万円 / 半日 |
| 半年見直し WS | 質問傾向の振り返り・FAQ 追加・エスカレーション再設計 | 30 万円 / 回 |

**原則: 月額に含めない。必要な顧客だけが都度購入する。**

## 5. 導入支援パッケージの詳細

### 5-1. 業務キックオフワークショップ（1 回 2 時間）

**目的:** 最小限の業務理解を取得する。

**アジェンダ:**
- 新人が最初の 1 ヶ月で詰まるポイントは何か（3〜5 個）
- 新人がよく聞く質問トップ 10
- 絶対に間違えてはいけない回答領域は何か
- 人に必ず回すべき質問は何か

**成果物:** 業務理解メモ（A4 2〜3 枚）

### 5-2. 初期資料アップロード支援（50 件まで、1 日）

**目的:** セルフサービス開始までの最初のハードルを超える。

**前提条件:**
- 資料はフォルダ整理済みの状態で持参
- 最新版が識別済み
- テキスト抽出可能な形式

**やること:**
- 顧客が持参した資料を一緒にアップロード
- 管理画面の使い方を実地で覚えてもらう
- 正本フラグの付け方を指導
- カテゴリ分類の確認

**やらないこと:**
- 資料の内容読み込み・要約作成
- 資料自体の作成・修正
- 51 件目以降のアップロード代行
- フォルダ未整理の資料の仕分け

### 5-3. FAQ 候補の初期整備ワークショップ（1 回 3 時間、30 件確定）

**目的:** 横スクロール FAQ の初期セットを作る。

**前提条件:**
- **顧客側が FAQ 30 件の原案を事前に作成して持参する**
- 原案に対する回答根拠の資料が特定済み
- 決裁権限者が同席する

**やること（WS の場で）:**
- 原案 30 件のレビュー・修正・確定
- 各 FAQ の回答を管理画面で確認
- 足りない資料の特定（追加アップロード対象の洗い出し）

**やらないこと:**
- FAQ の原案をゼロから作成する作業
- 31 件目以降の整備
- 回答内容の業務的な正誤判断（顧客責任）

**成果物:** 稼働開始時点で 30 件の FAQ が稼働している状態

### 5-4. エスカレーション先ルール設計ワークショップ（1 回 2 時間）

**目的:** 「答えられない質問を誰に回すか」を決める。

**やること:**
- 質問カテゴリ別のエスカレーション先（部署・担当者・連絡手段）
- 緊急度判定ルール
- Slack / Teams の通知先設定

**成果物:** エスカレーション設定が管理画面に入力済み

### 5-5. 管理画面トレーニング（2 回、各 1 時間）

- 1 回目: 資料アップロード・正本管理・カテゴリ調整
- 2 回目: 未回答ログの見方・質問傾向ダッシュボード

### 5-6. 稼働開始後フォローアップ（初月のみ、2 回 各 1 時間）

**目的:** 最初の 1 ヶ月でセルフサービス運用に乗せる。

- 2 週目: 初期稼働状況の確認・質問傾向のレビュー
- 4 週目: 未回答ログの対処方法・継続運用への移行確認

**2 ヶ月目以降は月額運用（商品2）に移行。追加の伴走は別料金メニューで対応。**

## 6. 責任分界

### 6-1. 契約上の責任分界

| 項目 | 顧客責任 | 我々の責任 |
|------|---------|----------|
| 資料の正本定義 | 管理画面で正本フラグを立てる | 正本以外を回答参照しない設計 |
| 資料の最新性保証 | 最新版をアップロードする | 受領した版で回答する |
| 更新反映 | 管理画面からアップロードする | アップロード即時に反映する |
| 古い資料による誤回答 | 更新漏れは顧客責任 | 更新アラートを出す責任 |
| 業務判断の最終責任 | 回答を鵜呑みにしない運用 | 出典の明示・「確認を推奨」の注記表示 |
| 機密情報の取り扱い | 入れてはいけない資料の選別 | 受領後の適切な管理 |
| 資料更新責任者の指名 | 1 名を指名する | 指名された担当者を管理画面に登録 |

### 6-2. 運用上の仕組み（システム自動化）

- 月次レポートはシステムが自動生成する（人手で書かない）
- 更新アラートはシステムが自動で出す（我々が見に行かない）
- 正本チェックは管理画面で顧客が行う
- 誤回答エスカレーションは管理画面からの申請フォームで受け付ける

## 7. 技術スタック

### 7-1. 採用技術

| 領域 | 技術 | 選定理由 |
|------|------|---------|
| フロント | Next.js (App Router) + React + Tailwind CSS | GrowDays 標準スタック |
| アプリ実行基盤 | AWS ECS (Fargate) | サーバーレスコンテナ。インフラ管理不要でスケール可能 |
| CDN | Amazon CloudFront | 静的アセット配信・SSL 終端 |
| 認証 | Auth.js（メールパスコード認証） | 初期はパスワードレス（メールにパスコード送付）のみ。生体認証・SSO は将来オプション |
| DB | Amazon Aurora PostgreSQL + pgvector | マネージド PostgreSQL。pgvector 拡張でベクトル検索対応 |
| ORM | Prisma | GrowDays 標準スタック |
| LLM | Claude API（claude-sonnet-4-6 を基準） | コスパと精度のバランス |
| ファイル保管 | Amazon S3（顧客ごとにプレフィックス分離 + KMS 暗号化） | 詳細は §7-4 参照 |
| ファイル取り込み | PDF / Word / Markdown / Excel のチャンク分割 → ベクトル埋め込み | |
| 監視・ログ | Amazon CloudWatch + Sentry | インフラ監視は CloudWatch、アプリエラーは Sentry |
| シークレット管理 | AWS Secrets Manager | DB 接続情報・API キー等 |
| パッケージ管理 | pnpm | GrowDays 標準 |
| テスト | Vitest（単体・結合）/ Playwright（E2E） | GrowDays 標準 |
| CI/CD | GitHub Actions → ECR → ECS デプロイ | |

### 7-2. 認証方式

| 対象 | 認証方式 | 備考 |
|------|---------|------|
| 管理画面（バックオフィス） | 組織認証 + メールパスコード認証 | 管理者のみアクセス |
| ユーザーフロント（新人・バイト） | 組織認証 + メールパスコード認証 | パスワード不要。メールにパスコードを送付 |

- **初期はメールパスコード認証のみ**で十分。疎い会社のバイトに生体認証を強制するのは導入障壁が高い
- **生体認証（WebAuthn / パスキー）は将来オプション**として対応可能にしておく
- **SSO（SAML / OIDC）も将来オプション**。大企業向け展開時に追加

### 7-3. セキュリティ設計（データ保管方式）

顧客の社内規約・マニュアルを預かるため、データの機密性は最重要。

#### 検討した 3 方式

| 方式 | 概要 | メリット | デメリット |
|------|------|---------|----------|
| A. 我々の S3 に格納（分離なし） | 全顧客のデータを 1 バケットに格納 | 構築がシンプル | データ分離が弱い。事故時の影響範囲が大きい |
| **B. 我々の S3 に格納（顧客ごと分離 + 暗号化）** | **顧客ごとに S3 プレフィックス分離 + KMS 暗号化 + アクセスログ** | **構築がシンプル + セキュリティ確保** | **我々が技術的にはアクセス可能（監査ログで証明）** |
| C. 顧客のストレージに見に行く | 顧客の S3 / Google Drive 等から取得 | 我々がデータを持たない | 顧客ごとに接続設定が必要。疎い会社に設定させるのは困難 |

#### 採用方式: B（顧客ごと分離 + 暗号化）

**初期は方式 B を採用。将来的に方式 C にも対応可能にしておく。**

- 顧客ごとに S3 プレフィックス（`s3://bucket/tenant-{id}/`）で分離
- **顧客ごとの KMS キーで暗号化**（サーバーサイド暗号化 SSE-KMS）
- S3 アクセスログを CloudTrail で記録（「誰がいつアクセスしたか」を証明可能）
- IAM ポリシーで**アプリケーションのみがアクセス可能**な構成にする（開発者の直接アクセスは原則禁止）
- 営業時の説明: 「AWS 上で顧客ごとに暗号化・分離して管理。アクセスログで監査可能です」

#### 将来対応: 方式 C（顧客ストレージ連携）

- 大企業やセキュリティ要件が厳しい顧客向けに、顧客側ストレージへの接続機能を後続で開発
- 対応候補: 顧客の S3 バケット / Google Drive / SharePoint
- **MVP では対応しない**

### 7-4. MVP で作るもの

- ChatGPT 風対話 UI（横スクロール FAQ 付き）
- 資料アップロード + 自動カテゴリ分類
- 正本フラグ・バージョン管理
- 未回答ログ
- 質問傾向ダッシュボード（最低限）
- Slack 連携
- 顧客ごとの S3 データ分離 + KMS 暗号化
- メールパスコード認証

### 7-5. MVP で作らないもの

- 生体認証（WebAuthn / パスキー）
- SSO 連携（SAML / OIDC）
- 顧客ストレージ直接連携（方式 C）
- オンプレ対応
- 多言語対応
- モバイルアプリ
- 高度な権限管理（まずは管理者 / 一般ユーザーの 2 ロール）
- Teams 連携（Slack を優先し、後続で対応）

### 8-2. 粗利構造の目安（現時点の試算値）

以下は試算であり、最初の 1〜2 社で実測して検証する。最初の 1〜2 社はテンプレ化の元手であり、想定粗利に達しない可能性がある。**目標粗利への到達は 3 社目以降の前提**とする。

- **月額運用:** 粗利 60〜70%（試算）
  - 自動化前提
  - 追加支援メニューは別途収益

### 8-3. スケール条件

- **導入支援パッケージのテンプレ化**が初期粗利を決める
- **運用期の自動化比率**が継続粗利を決める
- 管理画面のセルフサービス化が進めば、顧客が増えても我々の工数は比例しない

## 9. 失敗パターンと対策

| 失敗パターン | 対策 |
|------------|------|
| 導入支援が予定工数を超える | 回数・件数・時間の上限を契約書に明記。超過は別途見積 |
| 顧客の資料が整理されておらず持ち込めない | 事前準備条件を契約で定義。未達は着手延期 or スコーピング別途 |
| FAQ 原案を顧客が作れない | テンプレ（質問例リスト）を事前提供。WS は確定作業に限定 |
| WS で判断が下せず持ち帰りになる | 決裁権限者の同席を契約条件にする |
| 51 件目以降のアップロード要求 | 別途見積メニュー（時間課金） |
| コンサル的深掘り依頼 | 「それはスコープ外」を明示。別途見積メニューで対応 |
| セルフサービス運用に乗らない | 初月フォローアップで早期検知 + 追加支援メニューへ誘導 |
| 運用期に「未回答ログの見方が分からない」 | 追加支援メニュー（スポット相談 3 万/時間）で対応 |
| 資料が古いままで誤回答 → クレーム | 更新アラート + 有効期限機能 + 責任分界を契約に明記 |
| 「ChatGPT で十分」と判断される | 新人教育特化の UX（横スクロール FAQ）・出典表示・エスカレーション導線で差別化 |
| 粗利がスケールしない | 導入支援テンプレ化と運用自動化の比率を継続改善 |
| 最初の 1〜2 社で想定粗利に届かない | 学習投資と割り切る。3 社目で検証（判断ゲートに含める） |

## 11. まとめ

### 一言要約

**ChatGPT 風 UI の新人教育 SaaS を、初期は伴走付きで、運用は自動化で売る。伴走は定額・スコープ固定でコンサル化させない。**

### 5 つの固定事項

1. **我々はシステム屋**。運用期はコンサルしない
2. **ただし初期導入だけは伴走する**。スコープ固定・回数上限付きで
3. **ユーザー UI は ChatGPT / Claude 風**。横スクロール FAQ を目玉にする
4. **資料整備は管理画面の機能**で自動化する（自動分類・正本フラグ・更新アラート・未回答検知）
5. **商品は 2 つだけ**（初期構築 + 導入支援 / 月額運用）。追加支援は別料金メニュー
