1. エラーコード一覧（API 仕様）

HTTPcode説明発生例
400 VALIDATION_ERROR 入力値が不正（details.errors に詳細） 必須フィールドが空、形式エラー
400 PASSCODE_EXPIRED パスコードの有効期限切れ（10分） 期限後に verify を試みた
400 FILE_TOO_LARGE アップロードファイルが 2MB 超 資料アップロード
400 UNSUPPORTED_FILE_TYPE 非対応ファイル形式（PDF / TXT 以外） Word / Excel のアップロード
401 UNAUTHENTICATED 未認証 / セッション期限切れ Cookie なし、パスコード不一致
403 FORBIDDEN 認証済みだが権限不足 member が /admin/* にアクセス
404 NOT_FOUND リソース未存在（論理削除済みも含む） 存在しない FAQ ID、削除済みスレッド
409 CONFLICT 重複・競合 同名カテゴリ slug の作成
409 PASSCODE_ALREADY_USED 検証済みパスコードの再利用 verify 済みコードで再度 verify
429 RATE_LIMITED レート制限超過 質問 10 req/分超、パスコード 5 req/時間超
500 INTERNAL_ERROR サーバー内部エラー（詳細はログのみ） 予期しない例外、Zod バリデーション失敗
502 STORAGE_ERROR 外部ストレージ（Drive / Box）の操作失敗 OAuth トークン失効、フォルダが削除された
503 AI_UNAVAILABLE AI API（Groq / Anthropic）の障害・タイムアウト 質問送信時に AI API が 3 回リトライ後も失敗

2. レスポンス形式

標準エラー（4xx）

{
  "error": {
    "code":    "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": {
      "errors": [
        { "field": "question",   "message": "空文字列にできません" },
        { "field": "categoryId", "message": "存在しないカテゴリIDです" }
      ]
    }  // details は VALIDATION_ERROR のみ付く
  }
}
⚠ details.errors は常に配列 単一フィールドのエラーでも必ず配列で返す。クライアント側のパース処理を統一するため。

429 レートリミット

// ヘッダー
Retry-After: 30

// ボディ
{
  "error": {
    "code":    "RATE_LIMITED",
    "message": "リクエストが多すぎます。しばらく待ってから再試行してください。",
    "details": { "retryAfterSec": 30 }
  }
}

500 / 502 / 503（詳細は返さない）

{
  "error": {
    "code":    "INTERNAL_ERROR",  // or "AI_UNAVAILABLE" / "STORAGE_ERROR"
    "message": "サーバーエラーが発生しました"
    // ← スタックトレース・DB エラー・ファイルパスは絶対に含めない
  }
}

3. 例外クラス階層（実装） lib/errors.ts

5xx 系のサーバーエラーのみ例外クラスを使う。4xx（バリデーション・not-found）は Response.json() で直接返す。

AppError — 基底クラス。code / status / context を持ち toResponse() で JSON 化
AiUnavailableError 503 — Groq / Anthropic API が 3 回リトライ後も失敗
StorageError 502 — Google Drive / Box の操作失敗 
// lib/errors.ts — 実装

class AppError extends Error {
  constructor(code: string, status: number, message: string, context?: Record<string, unknown>) {
    super(message);
    // ...
  }
  toResponse(): Response {
    return Response.json({ error: { code: this.code, message: this.message } }, { status: this.status });
  }
}

// 使い方（ルートハンドラ内）
throw new AiUnavailableError({ provider: "groq", attempts: 3 });
throw new StorageError({ reason: "token_expired" });

4. エラー境界（errorBoundary）の仕組み lib/api.ts

すべての Route Handler は withApiHandler / withParamsHandler で包む。内部で errorBoundary が呼ばれ、例外を一元処理する。

throw AppError
→
errorBoundary がキャッチ
→
logger.error（context 付き）
→
err.toResponse() → 5xx JSON
throw 予期しない例外
→
errorBoundary がキャッチ
→
logger.error（stack 6行付き）
→
500 INTERNAL_ERROR
// lib/api.ts — ルートハンドラの書き方

// パラメータなし
export const GET = withApiHandler("GET /api/faqs", async (req) => {
  // ...
});

// 動的ルートパラメータあり
export const POST = withParamsHandler<{ threadId: string }>(
  "POST /api/threads/:threadId/queries",
  async (req, { threadId }) => {
    // ...
  }
);
requestId の自動付与 errorBoundary は各リクエストに requestId（8文字 UUID）を自動生成してログに含める。 将来的にレスポンスヘッダーに X-Request-Id として返すと問い合わせ時の追跡がしやすくなる。

4xx は例外を使わず直接返す

// ✅ 正しい書き方（4xx）
const parsed = PostSchema.safeParse(body);
if (!parsed.success) return validationError(parsed.error.issues.map(...));

const thread = await db.queryThread.findFirst(...);
if (!thread) return notFound("スレッドが見つかりません");

// ✅ 正しい書き方（5xx は throw）
throw new AiUnavailableError({ provider: effectiveProvider });

// ❌ NG — 4xx に throw を使わない
throw new Error("not found");  // → 500 INTERNAL_ERROR になってしまう

5. 構造化ログ・PII サニタイズ lib/logger.ts

ログは JSON 形式で出力し、CloudWatch Logs 等で検索しやすくする。context フィールドに入るデータは自動で PII サニタイズされる。

ログフォーマット

{
  "level":      "ERROR",
  "timestamp":  "2026-05-21T09:00:00.000Z",
  "requestId":  "a1b2c3d4",
  "path":       "POST /api/threads/:threadId/queries",
  "method":     "POST",
  "userId":     "usr_member",
  "durationMs": 423,
  "code":       "AI_UNAVAILABLE",
  "message":    "AIサービスが一時的に利用できません。",
  "context": {
    "provider": "groq",
    "attempts": 3,
    "apiKey":   "***"   // ← PII サニタイズ済み
  }
}

PII サニタイズの対象

以下のキーを含むフィールドは自動的に "***" に置換される（大文字小文字・部分一致）。

password
passcode
token
secret
credit
card
cvv
pin
apiKey
api_key
refreshToken
accessToken
encryptedRefreshToken

また、値が @ と . を含む文字列（メールアドレス形式）は自動的にマスクされる。

// マスク例
"minato@example.com"  →  "mi***@example.com"
"gsk_OKmy6Rp2yOZ..."  →  "***"  // apiKey にマッチ
絶対にログに出力してはいけない情報 パスワード・パスコード・APIキー・クレジットカード番号・リフレッシュトークン・暗号化前のトークン本体。 context にこれらを渡す場合は必ず上記キー名を使うこと（自動マスクが効く）。

6. 401 と 403 の使い分け

401 UNAUTHENTICATED — 認証できていない
Cookie なしセッション未開始
セッション期限切れ（7日）Cookie はあるが DB に記録なし
パスコード不一致verify 失敗
ログアウト後の操作Cookie が消えている
403 FORBIDDEN — 権限不足
member が /admin/* にアクセスadmin ロールがない
他ユーザーのスレッドを操作所有権がない
member が FAQ を作成しようとしたadmin 権限が必要な操作
member が資料を削除しようとしたadmin 権限が必要な操作
404 を使う場合 他ユーザーのリソースへのアクセスは、リソースの存在を知られないよう 403 ではなく 404 を返す設計もある。 本システムでは組織 ID スコープでフィルタしているため、スレッド・クエリは所有者チェックが失敗した場合に 404 を返す。

7. 401 受信時のクライアント挙動 lib/fetch.ts

API から 401 UNAUTHENTICATED を受け取ったとき、クライアントは即座にログインページへリダイレクトする。
lib/fetch.ts のグローバル fetch ラッパーで一元処理し、各コンポーネントには個別のハンドリングを書かない。

fetch リクエスト
→
401 受信
→
lib/fetch.ts ラッパー
→
router.replace("/login")
// lib/fetch.ts — 実装済み
async function apiFetch(url: string, init?: RequestInit) {
  const res = await fetch(url, init);
  if (res.status === 401) {
    // 管理画面は "/admin/login"
    const isAdmin = window.location.pathname.startsWith("/admin");
    window.location.replace(isAdmin ? "/admin/login" : "/login");
    throw new Error("UNAUTHENTICATED");
  }
  return res;
}
proxy.ts の HMAC 検証 proxy.ts は Cookie の HMAC-SHA256 署名を検証してセッションの正当性を確認する。 署名が無効な場合は即座に /login または /admin/login にリダイレクトする。 公開 API（/api/auth/passcode/*、/api/auth/webauthn/authenticate/* 等）はスルーする。

8. AI 障害時の挙動（AiUnavailableError）

askClaude() 呼び出し
→
3 回リトライ（500ms / 1000ms 待機）
→
全て失敗
→
throw AiUnavailableError
→
503 AI_UNAVAILABLE
状況レスポンス
Groq / Anthropic API がタイムアウト503 AI_UNAVAILABLE
Groq / Anthropic API がレート制限503 AI_UNAVAILABLE
Groq / Anthropic API がサービス停止503 AI_UNAVAILABLE
Claude の返答が Zod スキーマに合わない500 INTERNAL_ERROR
per-org の API キーが未設定でグローバルキーも未設定503 AI_UNAVAILABLE
ユーザー表示文言（クライアント側） 503 受信時は「現在 AI が混み合っています。少し待ってから再試行してください。」と表示する。 エラーコードをそのまま見せない。

9. ファイルアップロードのエラー

条件codeHTTP
ファイルサイズが 2MB 超 FILE_TOO_LARGE 400
PDF / TXT 以外の形式（MVP） UNSUPPORTED_FILE_TYPE 400
file フィールドが未指定 VALIDATION_ERROR 400
S3 アップロード失敗（S3_BUCKET 設定済みの場合） INTERNAL_ERROR 500
S3_BUCKET 未設定（ローカル開発） — エラーなし（テキスト抽出のみで DB 保存） 201
S3 の graceful degradation S3_BUCKET 環境変数が未設定のとき、アップロード処理を静かにスキップする。 ローカル開発ではテキスト抽出のみ行い、AI の回答は通常通り機能する。

10. レートリミット一覧

エンドポイント上限ウィンドウRetry-After
POST /threads/:id/queries 10 req 1分 / ユーザー あり
POST /auth/passcode/request 5 req 1時間 / メール あり
その他すべて 60 req 1分 / ユーザー あり

超過時は 429 RATE_LIMITED を返す。レスポンスヘッダーに Retry-After: <秒数> を付与する。

⚠ レートリミットは未実装 現在のコードにレートリミット処理は実装されていない。本番公開前に Redis + sliding window カウンター等で実装が必要。

11. 500 エラーの情報漏洩防止ルール

❌ レスポンスに返してはいけない情報
  • スタックトレース
  • DB エラーメッセージ（テーブル名・カラム名を含む）
  • 内部ファイルパス（/app/lib/... 等）
  • 環境変数の値
  • Prisma / SQL のクエリ文
  • Prisma エラークラス名（PrismaClientKnownRequestError）
✅ ログに出力すること（サーバーサイドのみ）
  • requestId（問い合わせ追跡用）
  • code（エラーの種別）
  • スタックトレース上位 6 行
  • durationMs（レイテンシ）
  • context（PII サニタイズ済み）
// ❌ NG — Prisma エラーをそのまま返している
catch (err) {
  return Response.json({ error: err.message }, { status: 500 });
  // → "PrismaClientKnownRequestError: Unique constraint failed on field 'email'"
}

// ✅ OK — errorBoundary が自動で汎用文言に変換する
// ルートハンドラ内では何もしなくてよい。throw するだけで OK。
throw new Error("something unexpected");
// → クライアントには { "code": "INTERNAL_ERROR", "message": "サーバーエラーが発生しました" }
// → ログには stack trace が出力される
